## Contract and acceptance

Registry fields: version/cutoff/predecessor/source-policy identity; append-only
venue identities, product versions, access assertions and new-venue requests.
Product versions carry stable product/venue IDs, source identifier, aliases, type,
effective boundaries/verification, recorded time/reference, contract metadata and
explicit source-operation support/permission. Product identity/type cannot drift
across revisions. Alias ownership is unique within relevant venue/source/time scope;
unknown effective dates conservatively overlap. No brand-stem or fuzzy resolution.

Lookups return candidate IDs and reasons; a brand with several products is ambiguous.
Unverified scope, absent/incomplete contract units, missing fees, unsupported
settlement, unavailable/contradictory access and unpermitted/unsupported operations
block readiness. Economic readiness is registry evidence completeness only, not a
calculator, accepted fill, regulatory determination or live authorization. Requests
remain independent even where a historical same-brand mapping exists.

Tests cover ambiguous brand/product, aliases/collisions, temporal boundaries,
append-only preservation, changed identity rejection, missing fees, unsupported
settlement, access/permission separation, empty state, deterministic seed/replay,
corruption/atomic failure and old canonical/economic table equality. No private
historical rerun or notebook execution needed for an isolated optional registry.
Manual dashboard acceptance is inapplicable; real venue evidence still requires
private owner/source review before any downstream adoption.
